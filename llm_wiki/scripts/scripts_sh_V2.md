# `scripts_sh_V2/` (current shell-script generation)

**Path:** `scripts_sh_V2/`

## What it is

The **newer, improved** generation of shell launch scripts (superseding most of `scripts_sh/`, see `scripts_sh.md`), targeting centralized training of the newer model architectures (ViT, Swin, VAV, DemNet) on the HPC SLURM cluster. No top-level README exists in this folder at time of writing — the summary below is derived directly from the scripts and their comments.

## Layout

- `0_launch_sbatch_cent.sh` — main SBATCH entry point for a centralized training run: picks a model (`model_name`, e.g. `"vav"`), an optimizer (`AdamW` or `SGD`) and an LR scheduler (`ExponentialLR` or `CosineAnnealingWarmRestarts`), generates a random seed, and submits the job. Contains inline notes/gotchas as comments, e.g. "for demnet you have to set `use_rgb_input` to false inside `dataset.toml`" and a pointer to a note in `demnet.sh` about `NUM_CLASSES`/`MERGE_AD_CLASS`.
- `0_launch_sbatch_cent_continuation.sh` — like the above, but for resuming/continuing a previously started run (checkpoint continuation) rather than starting fresh.
- `0_launch_debug.sh` / `0_launch_debug_continuation.sh` — debug-mode counterparts of the two scripts above, for local/interactive iteration rather than full SBATCH submission.
- `0_decompress.sh` — a one-off interactive-mode utility to decompress downloaded/preprocessed ADNI MRI zip archives (`Brain_MRI_Preprocess__GradWarp-B1-N3__-_SCALED_MRI_*.zip`) from `$SCRATCH/ADNI_MRI_NORMALIZED/` into `$SCRATCH/ADNI_MRI_NORMALIZED_DECOMPRESSED/`, using `7z`.
- `demnet_cent.sh`, `vit_cent.sh`, `swin_cent.sh`, `vav_cent.sh` — per-model SLURM job scripts (SBATCH directives: GPU partition `hopper`, qos `iris-hopper`, etc.) that actually run centralized training for DemNet / ViT / Swin / VAV respectively; these are what `0_launch_sbatch_cent*.sh` submits.
- `eternal_grokking.sh` + `eternal_grokking_job.sh` — "eternal" training runs for the grokking experiment (does very long training make DemNet / a small ViT generalize under the subject-aware split?), using idle GPUs. `eternal_grokking.sh` is the single entry point, run on the login node: `bash scripts_sh_V2/eternal_grokking.sh <action> <model>` with `<model>` in `demnet`, `vit` and actions:
  - `new <model> [n]` — create `n` runs with new random seeds: copies the config templates, writes optimizer/dataset/training configs from the variables at the top of the script (settings are **frozen** at creation), freezes a copy of the code (`.py` files of `src/` and `scripts_python/` + `GIT_INFO.txt` with commit and diff), appends the seed to `config/seed_list_grokking/<model>.txt` and submits.
  - `resume <model> [n]` — submit up to `n` seeds of the list that are not in the queue (checked with `squeue` on the job name, so running, pending and requeued jobs count as busy), not stopped (`STOP` file) and not finished (`FINISHED` file).
  - `import <model> <old_config_folder> <start_epoch>` — turn an old (non-eternal) run, e.g. `config/training_hpc/grokking_vit_<seed>/`, into an eternal run: keeps its configs, loads the older of its A/B backups through `path_past_weights`/`path_past_optimizer`, sets `start_epoch` (old backups do not store the epoch), reuses its idx files if present.
  - `stop <model> <seed>` — create the `STOP` file (clean stop at the end of the current epoch). Delete it and use `resume` to restart.
  - `status <model>` — SLURM state and STOP/FINISHED flags of every seed.
  Per-run files (job name `eternal_<model>_<seed>`, one folder and one wandb project per model — `DemNet_Grokking_Experiment`, `ViT_Grokking_Experiment`): `config/training_hpc/grokking/<model>/<job>/` (configs, `code/`, `idx/`, STOP/FINISHED), `model_weights/grokking/<model>/<job>/` (A/B backups and checkpoints, `model_BEST.pth`), `${SCRATCH}/grokking/<model>/<job>/` (snapshots every `snapshot_every` epochs, local wandb files), `output/grokking/<model>/` (SLURM logs, `--open-mode=append`).
  `eternal_grokking_job.sh` is the job body (never launched directly). It uses `--requeue` (preempted `besteffort` jobs are requeued) and `--signal=B:USR1@600` + a `trap` that calls `scontrol requeue` 10 minutes before the time limit (a TIMEOUT is not requeued by `--requeue`); training runs in background so the trap can fire. It uses the frozen code through `PYTHONPATH` (no `pip install`), puts `WANDB_DIR`/cache/data/artifact dirs on `$SCRATCH` and wipes them at every start, sets `WANDB_CONSOLE=off`, creates the idx files only once, and does **not** requeue after a crash. Training resumes through `resume_from_backup` (see `addl/training/train_functions.md`).
- `config/` — TOML configuration files consumed by the scripts above:
  - Top-level reusable configs: `dataset.toml`, `server.toml`, `training.toml`, `optimizer_AdamW.toml` / `optimizer_AdamW_backup.toml` / `optimizer_SGD.toml`, `lr_sched_ExponentialLR.toml` / `lr_sched_CosineAnnealingWarmRestarts.toml`, one `model_*.toml` per architecture (`model_demnet.toml`, `model_demnet_tiny.toml`, `model_swin.toml`, `model_vav.toml`, `model_vgg.toml`, `model_vit.toml`, `model_vit_micro.toml`, `model_vit_tiny.toml`), plus `chained_lr_scheduler_example.toml`.
  - `config/debug/train_<model>_<random_id>/` — a large number of **auto-generated, per-run** config snapshots (`dataset.toml`, `lr_scheduler.toml`, `model.toml`, `optimizer.toml`, `training.toml`), one directory per debug run, named by a random numeric id. These are run artifacts, not hand-maintained config — do not treat them as a place to edit defaults.
  - `config/seed_list_grokking/` — one file per model (`demnet.txt`, `vit.txt`), one seed per line: registry of all the eternal grokking runs, read by `eternal_grokking.sh resume`/`status`. Untracked by git on purpose (it is appended on the HPC).
  - `config/training_hpc/` — gitignored, per-run frozen configs created by the launchers (e.g. `grokking_<model>_<seed>/` from the old continuation workflow, `grokking/<model>/eternal_<model>_<seed>/` from `eternal_grokking.sh`).

## Notes for future work

- This is the folder to extend when adding a new model/training variant going forward, following the `0_launch_sbatch_cent.sh` → per-model `*_cent.sh` → `config/model_*.toml` pattern already established for demnet/vit/swin/vav.
- `config/debug/train_*_<id>/` directories are generated, numerous, and disposable — don't document or rely on specific ones; they're a side effect of running debug launches, not source of truth.
- `eternal_grokking.sh` was dry-run tested with mocked `sbatch`/`squeue`/`scontrol` but, at time of writing, not yet run on the real cluster. The defaults at the top of the script (weight decay, 50/50 split, partition/qos) are placeholders pending a discussion of the scientific settings. It supersedes `0_launch_sbatch_cent_continuation.sh` for grokking runs.
